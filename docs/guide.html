How this rate limiter works

A guided tour of the codebase — the request path end to end, what every file does, and the reasoning behind each decision. Written so that by the end you can answer “what is this for and why is it like that?” about any part of the repo.

1 · Start here

You already know a rate limiter decides “has this caller had too many requests?”. Everything in this repo exists to answer that question correctly when there is more than one server, when the database holding the counts is slow or down, and when the caller is actively trying to get more than its share.

The one idea that organises the whole codebase

There is exactly one interface. Everything implements it:

type Limiter interface {
    Allow(ctx, key)        (Result, error)  // shorthand for AllowN(…, 1)
    AllowN(ctx, key, n)    (Result, error)  // consume n units of quota
    Name()                 string           // metrics label
}

Two things are real limiters that count requests. Everything else is a decorator: it takes a Limiter, adds one behaviour, and is itself a Limiter. That is why they stack in any order, and why each file stays small enough to reason about alone.

The 2 real algorithms

sliding_window_counter token_bucket

Each has an in-memory version (single process) and a Redis version (shared across servers). They count, and they decide.

The 5 decorators

chained adaptive fallback lease penalty

Tiers, load shedding, outage handling, round-trip reduction, abuse escalation. None of them counts requests themselves.

Why a decorator chain instead of one big function? Each concern can be switched off in config without touching the others, and each can be tested against a fake Limiter in isolation. The whole test suite for load shedding never touches Redis. The cost is that you must read main.go to know the assembled order — which is why section 3 exists.

The 30-second mental model

  1. An HTTP request arrives. The middleware turns it into a key (who is this?) and a cost (how much quota does this endpoint charge?).
  2. That (key, cost) goes into the top of the chain.
  3. Each layer either answers immediately, or passes it down.
  4. At the bottom, a Lua script in Redis atomically checks and updates the count.
  5. A Result comes back up. The middleware turns it into a status code and headers.

3 · The chain, and why the order matters

Click any layer to see why it sits where it does. The order is not arbitrary — three of these positions are load-bearing, and moving them silently breaks a feature.

The trap worth remembering. If the adaptive limiter were placed above the lease cache, it would be timing lease hits — around a microsecond — instead of Redis round trips. Its average would never approach the “Redis is slow” watermark, so load shedding would never once engage. The code would look perfectly correct and the feature would be dead. This is the kind of bug that only shows up if you reason about what each layer measures, not just what it does.

4 · The two algorithms

These are the only components that actually count. Everything else defers to them.

Sliding window counter

Keeps two numbers per key: how many requests in the current fixed window, and how many in the previous one. It then interpolates between them:

effective = round( prev_count × (1 − elapsed/window) ) + curr_count

If you are 25% into the current window, 75% of the previous window still “counts”. As time moves, the old window's contribution smoothly decays.

Why not just a fixed window? A plain fixed window resets to zero on a boundary. A caller can spend its entire quota in the last instant of one window and its entire quota again in the first instant of the next — 2× the limit in a millisecond. The interpolation removes that cliff while still costing only two integers per key.

Why round and not floor? Truncating always throws away a fraction of the carried-over count, so the effective total is always slightly under the truth, so the limiter admits slightly more than the limit — every window, in the same direction. Rounding makes the error symmetric and self-cancelling. This is a one-character difference with a real bias behind it.

Token bucket

A bucket holds tokens up to burst_max. Tokens refill continuously at limit/window per second. A request takes cost tokens, or is refused.

// refill is computed lazily from elapsed time, never by a background ticker
tokens = min(burst_max, tokens + elapsed_ms × refill_per_ms)

Why lazy refill? A ticker per key would mean a goroutine (or a timer) per key — millions of them. Computing now − last_seen on access gives the identical answer for zero ongoing cost, and idle keys cost literally nothing.

The detail that makes the fallback work. Both algorithms align their windows to the same absolute epoch boundaries — in memory and in Redis. So when Redis dies and a node starts enforcing locally, the key keeps the same window boundaries it already had. The fallback is a continuation of the distributed limiter rather than a reset of it. If the in-memory version started its window at “now”, every key would get a fresh quota the instant Redis blinked.

5 · Redis and the Lua scripts

Three Lua scripts do the real work. Each runs atomically — Redis is single-threaded, so while a script runs, nothing else can interleave.

ScriptLinesJob
limiter/sliding_window.lua87Read both windows, interpolate, decide, increment, set expiry
limiter/token_bucket.lua66Read bucket, refill by elapsed time, decide, consume, write back
penalty/penalty.lua50Bump the offence count, compute the escalating penalty, store it

Why it must be one atomic step

Two separate commands create two separate races:

Race 1 — check then increment

-- node A GET count  → 99
-- node B GET count  → 99
-- both think there is room
-- node A INCR       → 100
-- node B INCR       → 101  ✗

Both nodes see “one slot left” and both take it. The limit is exceeded.

Race 2 — increment then expire

-- node A INCR    → 1
-- node B INCR    → 2
-- node A EXPIRE  → TTL set
-- node B EXPIRE  → TTL reset ✗

The window silently extends every time a second node writes.

How the expiry is handled here, and why it changed. A common trick is to set the TTL only on the first write (if new_count == cost), saving one command. This repo instead calls PEXPIRE unconditionally, with a deadline computed from the window start: win + 2×window − now. Because that is a fixed absolute deadline, recomputing it is harmless — the TTL shortens as time passes rather than being pushed out. The clever version leaks the key forever if that single PEXPIRE is ever lost, which happens whenever the key was created by anything other than this script. One extra O(1) command buys away a whole class of slow memory leak.

Whose clock decides?

The scripts call redis.call('TIME') instead of taking the time from the application server.

Why. If each node sent its own clock, two nodes whose clocks differ by 200ms would disagree about which window a request belongs to — so the same request could be counted in different windows depending on which server received it. Redis is the one thing all nodes already share, so making it the clock makes boundaries globally consistent. The cost is that the script becomes non-deterministic, which is fine on Redis 5+ where replicas receive the resulting writes rather than the script itself. That version requirement is a real constraint the code documents.

Key layout

rl:{user:alice}:1716000060   ← sliding window, current window bucket
rl:{user:alice}:1716000059   ← previous window
tb:{user:alice}              ← token bucket hash (tokens + timestamp)
pen:{user:alice}:p           ← active penalty (TTL = remaining time)
pen:{user:alice}:n           ← offence count, for escalation

Why the curly braces? That is a Redis Cluster hash tag. Cluster shards by key, but only hashes the part inside {…}. Since the scripts derive extra keys themselves (the two window buckets), the tag guarantees every derived key lands on the same shard — otherwise a clustered Redis would reject the script for touching multiple slots. The project does not ship a cluster client, but the keys are already shaped for one.

6 · Quota leasing — the most interesting part

If you only deeply understand one thing in this repo, make it this. It is the part that is easy to get wrong in a way that looks fine.

The obvious idea, and why it is broken

Hitting Redis on every request is expensive. The obvious fix: cache the decision for a few milliseconds. Here is what that actually does, with a 5ms cache and one key receiving 1000 requests/second:

every 5ms window:  5 requests arrive
                   1 reaches Redis and is counted
                   4 are served from cache, counted nowhere

over one second:   200 counted, 800 invisible
configured limit:  100/s
actually admitted: 1000/s

Why this is the worst possible failure. The error grows with per-key request rate — so the limiter becomes least accurate exactly when a caller is hammering it hardest, which is the only situation it exists for. And nothing looks wrong: no errors, no logs, plenty of 429s being returned to make it seem like it is working.

The fix: lease quota instead of caching decisions

On a miss, ask Redis for the current request plus a few extra units. Those extras are already counted centrally, so they can be handed out locally with no loss of accuracy.

request 1  → ask Redis for 1 + 4 = 5 units   Redis count += 5
             use 1, keep 4 in local memory
request 2  → take 1 from the local lease      no Redis call
request 3  → take 1 from the local lease      no Redis call
request 4  → take 1 from the local lease      no Redis call
request 5  → take 1 from the local lease      no Redis call
request 6  → lease empty, ask Redis again

Five requests, one round trip, and Redis's count is exactly 5. The limit can never be exceeded, because nothing is ever handed out that was not counted first.

Direction of error

under-admits

If a key goes quiet with 3 unused units, those are lost. Fewer requests allowed than permitted — the safe direction.

Round trips saved

~prefetch/(prefetch+1)

With prefetch: 4, about four in five requests to a hot key never touch Redis.

Measured

45.7 ns vs 88 µs

A lease hit is ~1,900× cheaper than a round trip, and allocation-free.

Three refinements, each fixing a real measured problem

a · Accumulate, never replace

When several requests miss at once, each draws its own batch. If storing a new lease overwrote the old one, the leftover units of the old lease would be discarded — quota already consumed in Redis, thrown in the bin. Measured effect: the limiter admitted 108 against a limit of 100 in one direction and stranded 85 units in the other. Now batches add together.

b · Warm up before batching

A key's first miss claims no extra units. Why: in a simultaneous burst on a brand new key, every concurrent request misses before any lease exists, so each grabs a full batch and the burst ends before anyone spends them. Measured: 15 admitted out of a limit of 100. With warm-up: 76–100.

c · Shrink the batch near the limit

The prefetch is capped by the headroom Redis last reported. Close to the limit a big batch cannot be spent before the window turns, so it would strand quota. With this, sustained traffic lands on exactly the limit — verified at prefetch 1, 4, 8 and 16.

The other half: negative caching

Once a caller is over quota, its denial is cached locally — capped at its own Retry-After so it is never held past the moment quota would have returned. This is what makes abuse cheap to refuse: an attacker sending 10,000 requests/second costs almost no Redis traffic at all.

7 · Staying up when things go wrong

Three failure strategies

StrategyRedis is down, so…Choose when
fail_openadmit everything (200)Refusing real traffic costs more than briefly over-serving — search, feeds, content
fail_closedrefuse everything (503)An unmetered request is dangerous — payments, auth, anything that spends money
local_fallbackeach node enforces from its own memoryMiddle ground; N nodes admit roughly N× the limit

The single worst bug this project had. The middleware used to call next.ServeHTTP(w, r) on any limiter error. So during a Redis outage every request was admitted — regardless of the configured strategy. fail_closed silently became fail_open, on precisely the services that chose it because unmetered requests are dangerous. The fix is structural, not a patched condition: a handled failure now returns a decision with a nil error, so there is no way for a caller to check only the error and let the request through.

The circuit breaker

After a few consecutive failures, Redis is skipped entirely until a cooldown passes, when exactly one probe is let through to test recovery.

Why this is not optional. Without it, every request during an outage waits out the full Redis timeout before falling back. So a dependency you have explicitly decided to survive without instead adds its timeout to every single response. The breaker turns a latency catastrophe into a fast local decision. Two things are deliberately excluded from tripping it: client cancellations (a client-side timeout storm would degrade everyone else) and impossible-cost errors (one bad caller must not break the limiter for all).

Adaptive load shedding

Watches how long the limiter takes and drops a fraction of traffic when Redis slows down — the same AIMD control law as TCP congestion control: back off sharply, recover gently.

latency > high watermark → multiplier ×= 0.75  |  latency < low watermark → multiplier += 0.05

The subtle fix here. The multiplier used to be stepped once per request. That ties the control loop's speed to traffic volume: at 100k requests/second it slams to the floor within a millisecond, and a nearly idle service never recovers at all because recovery needs one request per step. Now it steps at most once per fixed interval, so decay and recovery are measured in time — which is what makes it a controller rather than a counter.

The penalty box

A caller that keeps hammering after being refused is not deterred by more 429s, and costs a round trip either way. After N denials in a window, the key is blocked outright — doubling on each further offence, up to a cap.

The fairness rule. Only denials the caller is responsible for count as strikes. Load shedding and limiter outages are the service's own condition — counting those would march well-behaved callers into the penalty box during an overload and keep them locked out for minutes after it passed. That is the exact opposite of what shedding is for. See limiter.CallerAttributable.

An honest trade-off. Strikes are counted per node, and Redis is only written when the threshold trips. That keeps abuse cheap to shed, but it means an offender spread evenly across N nodes needs up to N×threshold denials to trip. Once tripped, the penalty is shared globally. Knowing where a design is approximate — and why that was chosen — is more valuable than pretending it is exact.

8 · The HTTP layer

Turning a request into a key

key_type: ip      → ip:203.0.113.9
key_type: user    → user:alice                    (falls back to ip if no header)
key_type: tenant  → tenant:acme|user:alice

Why X-Forwarded-For is ignored by default. Anyone can send that header. If the limiter trusts it, a caller gets a brand new rate limit key — and therefore a fresh quota — just by changing it on every request. Complete bypass, no tooling required. So trusting it is opt-in via trusted_proxy_hops, and the address is read by counting from the right: each proxy appends the address it saw, so the rightmost entries are the ones written by your own infrastructure and cannot be forged. Reading the leftmost entry — the common shortcut — reads whatever the client typed.

Why key components are length-bounded and hashed. These values become Redis key names. Unbounded, a caller sends a megabyte-long X-User-ID — under thousands of distinct values — and exhausts Redis memory rather than merely burning quota. Note it hashes rather than truncates: truncation would merge everyone sharing a prefix into one quota, which is simultaneously a bypass and a denial of service. And each component is bounded separately so the tenant:…|user:… structure survives — hashing the whole key would erase the tenant, and the chain's per-tenant tier would collapse every big-header caller into one shared bucket.

StatusMeansWhy not something else

X-RateLimit-Limit / -Remaining / -ResetWhenever a real numeric limit applies

X-RateLimit-Denied-ByWhen a specific stage or tier refused it

Two small decisions with reasons. Retry-After rounds up: rounding down tells the client to retry before quota is actually available, which earns it another denial and — with the penalty box on — another strike. And the X-RateLimit-* headers are omitted during a fail-open degradation rather than guessed, because there is no counted quota behind that decision and a number the client may cache and act on would be a lie.

Why /healthz deliberately does not check Redis. Liveness answers “is this process healthy?”. If it checked Redis, a Redis outage would make the orchestrator restart every node — during the exact incident the fallback strategy exists to ride out. /readyz does check Redis, because readiness answers a different question: “should traffic come here?”. Health and metrics endpoints are never rate limited, since they must answer precisely when everything else is being throttled.

9 · Config, and why validation is so strict

The reason for all of it: a misconfigured rate limiter still returns 200s. Nothing looks broken until the thing it was protecting falls over. So the config layer is deliberately hostile to mistakes.

  • Unknown keys are a startup error. A misspelled setting you believe you enabled would otherwise silently not exist.
  • Every enum is parsed, never defaulted. A typo in fail_closed must not quietly become allow-everything.
  • Combinations are checked. A route whose cost exceeds capacity could never be served; a per-tenant tier with no tenant in the key would put every caller in one bucket.
  • All problems are reported at once, so you do not fix one per restart.
$ ./bin/server -check
invalid configuration:
limiter.algorithm: unknown algorithm "fixed_window" (want "sliding_window_counter" or "token_bucket")
limiter.chain.enabled requires limiter.key_type: "tenant", got "ip" — without a tenant in
  the key every caller shares one tenant bucket
routes[0] "/api/export": cost 200 exceeds the per-window capacity 100, so every request
  to it would be rejected

Every value is also overridable by environment variable: limiter.limit → RATELIMITER_LIMITER_LIMIT. Environment values go through the identical validation.

Two implementation choices worth knowing. Label children are resolved once at startup, not per request — WithLabelValues hashes the label set on every call, which is pure waste when the labels never change. And anything derived from live state is a CounterFunc/GaugeFunc, computed at scrape time, so it cannot go stale or drift from its source and needs no background goroutine.
